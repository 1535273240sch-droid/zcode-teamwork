### 2.2 ⚠️ 两个必须做的动作

   未批准前钩子不执行。**这是最容易被忽略的一步**，不批准的话装了跟没装一样。

## 三、要回答的 4 个问题（按重要性排序）

### Q1 ⭐ 7 个钩子事件是否都真的送达？

**看**：`.zcode-probe/events.jsonl` 里出现过哪些 `hookEventName`。

期望值：`SessionStart` / `UserPromptSubmit` / `PreToolUse` / `PermissionRequest` /
`PostToolUse` / `PostToolUseFailure` / `Stop`

**如果只收到部分** → 说明第三方插件的事件集比内建插件小，需要调整架构。

### Q2 ⭐⭐ `Stop` + `decision:"block"` 能否真的拦住收尾？

这是**整个插件最核心的机制**（"没验证就不许说完成"）。做法：

```bash
echo '{"mode":"block"}' > .zcode-probe/mode.json
```

开新会话，让模型随便回答一句话。**如果它被拦住并继续输出** → 机制成立。
**如果它正常结束** → 这个机制不成立，需要换实现路径。

> 验证完记得删掉 `mode.json`，否则会一直拦。

### Q3 ⭐ `PreToolUse` 的拒绝与改写是否生效？

```bash
echo '{"mode":"deny"}' > .zcode-probe/mode.json      # 测拒绝
echo '{"mode":"rewrite"}' > .zcode-probe/mode.json   # 测改写
```

- `deny`：模型想写文件时应被拒
- `rewrite`：写文件时应带上 `_probe_rewritten` 标记（检查文件内容）

### Q4 `additionalContext` 是否真的进了模型上下文？

```bash
echo '{"mode":"context"}' > .zcode-probe/mode.json
```

开新会话，问模型「你的上下文里有没有 hook-probe 相关的内容」。

## 四、字段名陷阱（已踩过，务必注意）

代码里用了 `pick(input, 'camelCase', 'snake_case')` 同时兼容两种拼写，原因是：

- ZCode 的 **TypeScript 契约**是 camelCase：`hookEventName` / `stopHookActive` / `toolInput`
- **process 钩子的实际载荷**是 snake_case：`hook_event_name` / `stop_hook_active` / `tool_input`

**如果你发现钩子"静默失效"（不报错但也不生效），第一个要查的就是字段名。**

对比 `first-seen.json` 里的 `keys` 数组和代码里 `pick()` 读的键名。

## 六、已知的限制（不是 bug）

| 限制 | 原因 |
| --- | --- |
| **没有 dead-man 计时器** | 进程钩子是一次性的，握不住定时器。`progress-watch` 只能在用户回合报告停滞。 |
| 没有常驻进程 | 同上。原版的 600 秒自动接管做不到。 |
| 大改动仍需人工批准 | 设计如此：`approve` 是唯一允许执行的门。 |

## 九、真机验证实测结论（2026-09-21，Windows 10 / ZCode 3.14.1）

以下为第一次真实环境验证的结果，供后续复核参考。

### 9.1 Stop 只在完整 turn 收口时触发

多轮工具交互（例如访谈流中的 AskUserQuestion）**中途不会触发 Stop**。
曾因此误判「Stop 从不送达」——那是误报。

**正确测法**：开新会话，发**一句纯文本**让模型直接回答（不涉及任何工具），
等它答完，几秒后 Stop 到达（`toolCallCount: 0`）。

如果始终收不到 Stop，检查是否命中了 `automationCreateLimitReached`
（自动化模式的创建上限），该状态下 ZCode 会跳过 Stop 钩子。

### 9.2 `reason` 才是生效的字段，`stopReason` 不行

实测对照：

| 返回字段 | 结果 |
| --- | --- |
| `{decision:"block", stopReason:"..."}` | ❌ 模型正常收尾，只触发一次 Stop |
| `{decision:"block", reason:"..."}` | ✅ **同一回合 Stop 连续触发 4 次**，`stopHookActive` 由 False → True |

原因：ZCode 只有 `reason` 和 `systemMessage` 会进 `additionalContexts`，
而续跑判定是 `stopShouldContinue && additionalContexts.length > 0 && attempts < 3`。
`stopReason` 仅用于显示。

> 本仓库 v0.3.0 之前用的正是 `stopReason` —— 验证门禁在真机上是哑的。已在 `ca0ffd32` 后续提交修复。

### 9.3 字段名：双拼写同时存在

`first-seen.json` 实测 keys：`hookEventName` + `hook_event_name`、`sessionId` + `session_id`、
`transcriptPath` + `transcript_path`、`toolName` + `tool_name`、`toolInput` + `tool_input`、
`stopHookActive` + `stop_hook_active`。

- camelCase 的 `toolCallId` 对应 snake 是 **`tool_use_id`**（不是 `tool_call_id`）
- **`cwd` 在所有事件里都存在**（实测 31/31）
- 另有 `mode`、`permission_mode`、`riskLevel`、`sideEffectScope`、`turnId`、`traceId`、`model`

### 9.4 其它实测结论

- `deny` 拒绝**物理生效**：模型尝试写入的文件确实未被创建
- `additionalContext` **确实进入模型上下文**，模型能逐条引用
- `updateInput` 代码层支持（有真实替换分支），但被所有权锁的 deny 分支抢先，需在无 `.teamwork` 的目录单独验证
- 钩子执行**不写 ZCode 日志**（`~/.zcode/cli/log/` 搜不到），无法从日志侧诊断
- `transcript_path` 每会话独立临时目录
- 子代理（Task）是否共用同一 transcript **仍未验证**

### 9.5 CLI 里程碑 schema

`plan --milestones <file>` 要求**纯 JSON 数组**（不是 `{"milestones":[...]}`），
条目字段是 **`owner_role` / `verified_by`**（不是 `owner` / `verifier`）。

```json
[
  {
    "id": "m1",
    "deliverable": "port the loader",
    "status": "pending",
    "owner_role": "worker",
    "verified_by": "critic",
    "acceptance": "npm test passes with the new loader",
    "files": ["src/loader.ts"],
    "blocked_by": []
  }
]
```

> 里程碑状态以 `.teamwork/campaign.json` 为准（引擎写入处），
> `.teamwork/plan.json` 仅为旧版兼容保留。
