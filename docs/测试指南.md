## 二、装上 ZCode，跑第一次真机验证

### 2.1 安装

在 ZCode 里打开任意项目 → **Settings → Plugins → Create → Add marketplace**，填：

```
1535273240sch-droid/zcode-teamwork
```

在 **Personal** 分区找到 `teamwork` 和 `hook-probe` → 都点 **Install** → 打开开关。

### 2.2 ⚠️ 两个必须做的动作

1. **开新会话** —— ZCode 的钩子配置是会话启动时快照的，当前会话不会热加载。
2. **批准钩子信任** —— ZCode 对工作区钩子有信任闸门（`workspace_hooks_pending_trust`），
   未批准前钩子不执行。**这是最容易被忽略的一步**，不批准的话装了跟没装一样。

### 2.3 跑一轮

随便做点操作：改一个文件、跑一条命令、让模型回答一句话。

```bash
cat .zcode-probe/events.jsonl      # 收到了哪些事件
cat .zcode-probe/first-seen.json   # 首个事件的字段清单
```

## 三、要回答的 4 个问题（按重要性排序）

### Q1 ⭐ 7 个钩子事件是否都真的送达？

**看**：`.zcode-probe/events.jsonl` 里出现过哪些 `hookEventName`。

期望值：`SessionStart` / `UserPromptSubmit` / `PreToolUse` / `PermissionRequest` /
`PostToolUse` / `PostToolUseFailure` / `Stop`

**如果只收到部分** → 说明第三方插件的事件集比内建插件小，需要调整架构。

### Q2 ⭐⭐ `Stop` + `decision:"block"` 能否真的拦住收尾？

这是**整个插件最核心的机制**（"没验证就不许说完成"）。做法：

```bash
echo '{"mode":"block"}' > .zcode-probe/mode.json
```

开新会话，让模型随便回答一句话。**如果它被拦住并继续输出** → 机制成立。
**如果它正常结束** → 这个机制不成立，需要换实现路径。

> 验证完记得删掉 `mode.json`，否则会一直拦。

### Q3 ⭐ `PreToolUse` 的拒绝与改写是否生效？

```bash
echo '{"mode":"deny"}' > .zcode-probe/mode.json      # 测拒绝
echo '{"mode":"rewrite"}' > .zcode-probe/mode.json   # 测改写
```

- `deny`：模型想写文件时应被拒
- `rewrite`：写文件时应带上 `_probe_rewritten` 标记（检查文件内容）

### Q4 `additionalContext` 是否真的进了模型上下文？

```bash
echo '{"mode":"context"}' > .zcode-probe/mode.json
```

开新会话，问模型「你的上下文里有没有 hook-probe 相关的内容」。

## 四、字段名陷阱（已踩过，务必注意）

代码里用了 `pick(input, 'camelCase', 'snake_case')` 同时兼容两种拼写，原因是：

- ZCode 的 **TypeScript 契约**是 camelCase：`hookEventName` / `stopHookActive` / `toolInput`
- **process 钩子的实际载荷**是 snake_case：`hook_event_name` / `stop_hook_active` / `tool_input`

**如果你发现钩子"静默失效"（不报错但也不生效），第一个要查的就是字段名。**

对比 `first-seen.json` 里的 `keys` 数组和代码里 `pick()` 读的键名。

## 五、端到端跑一轮真实 campaign

真机验证通过后，测完整流程：

```bash
CLI=plugins/teamwork/lib/teamwork-cli.mjs

node $CLI init --objective "给 utils 里的日期解析函数补一组边界测试"
node $CLI pattern --suggest "给 utils 里的日期解析函数补一组边界测试"
node $CLI decompose                    # 看草稿
node $CLI plan --milestones m.json     # 提交计划
node $CLI approve                      # 批准（此时才允许执行）
node $CLI schedule                     # 看批次
```

然后在 ZCode 里跑 `/teamwork <目标>`，观察：

1. **访谈**是否正常提问
2. **Sentinel 审宪章**是否返回 `CLEARED` / `BLOCKED`
3. **文件独占**是否真的拦住越界写入（两个 Worker 写同一文件时）
4. **验证门禁**是否在缺少验证记录时拦住收尾
5. **派发预算**是否在超出时拒绝

## 六、已知的限制（不是 bug）

| 限制 | 原因 |
| --- | --- |
| **没有 dead-man 计时器** | 进程钩子是一次性的，握不住定时器。`progress-watch` 只能在用户回合报告停滞。 |
| 没有常驻进程 | 同上。原版的 600 秒自动接管做不到。 |
| 大改动仍需人工批准 | 设计如此：`approve` 是唯一允许执行的门。 |

---

## 七、发现问题怎么办

1. 先看 `.teamwork/journal.jsonl` —— 追加式日志，记录每一步
2. 再看 `.zcode-probe/events.jsonl` —— 钩子实际收到什么
3. 对比 `lib/` 里的代码期望什么

**如果是字段名或事件集的问题**，通常只需要改 `pick()` 的参数或 `hooks.json` 的注册。
