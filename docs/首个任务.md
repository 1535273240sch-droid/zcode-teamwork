# 首个任务

> 第一次用 Teamwork 时跑这个。**目标不是产出，是让你看清它到底怎么工作。**
>
> 任务故意选得小、边界清晰、验收可验证。跑完你就知道它值不值得用在真活上。

---

## 为什么是这个任务

| 考虑 | 说明 |
| --- | --- |
| **安全** | 目标仓库就是本仓库。跑坏了也不碰你的真实项目 |
| **小** | 2 个里程碑，串行，不涉及并发写 |
| **可验证** | 验收标准是 `npm test` 通过 + 新测试先失败后通过 |
| **有真实空白** | `lib/journal.mjs` 确实有未覆盖的边界分支 |

---

## 前置检查（四项，缺一不可）

```bash
# 1. 版本必须是 v0.3.5 或以上（含全部真机修复）
node -p "require('./package.json').version"

# 2. node 在 PATH 上 ← 这是 2026-09-22 真跑里最实际的坑
node --version

# 3. 本地测试：831 通过 / 1 跳过（跳过项是 git 隔离测试，机器无 git 时必然跳过）
npm test

# 4. ZCode 里已经：
#    - 安装本仓库为 marketplace
#    - 安装 teamwork 插件
#    - 【重启 ZCode】← 不只是开新会话：PATH 是进程启动时继承的，
#      装了 node 但不重启，钩子仍找不到 node
```

> ### 第 2 项是真跑里踩到的坑，值得单独说
>
> 7 个钩子全部以 `type: "process"` 调用**裸 `node`**。机器上没有 Node.js 时，
> 每次钩子调用都失败，而且**不报错、不提示**——日志里只有 `hook.run.failed`，
> 从用户视角看就是「装好了但没反应」。那次真跑里 **287 次钩子调用全部静默失败**。
>
> `node --version` 能打印版本号，才算真的就绪。

> ### 关于「批准钩子信任」
>
> 老版本这份文档要求批准钩子信任。实测在 ZCode 3.14.1 上**插件钩子无需额外批准
> 即可执行**（`zcode-guide` 亦确认所有插件钩子均可运行）。
> 若钩子「没反应」，先查第 2 项，而不是去找信任闸门。

## 第 1 步：建立 campaign

```bash
CLI=plugins/teamwork/lib/teamwork-cli.mjs

node $CLI init --objective "补齐 lib/journal.mjs 的边界测试：先把未覆盖的分支找出来并逐条说明触发输入，再为其中每一条写一个测试"
```

**看点**：`init` 会创建 `.teamwork/campaign.json`，此时是 `scoping` 阶段，**还不能执行**。

## 第 2 步：看拆解草稿，然后自己定计划

```bash
node $CLI decompose
```

它会按规则给一版草稿。**草稿只是脚手架**，真实计划用下面这份。

## 第 3 步：写里程碑文件

存成 `milestones.json`：

```json
[
  {
    "id": "survey",
    "deliverable": "列出 lib/journal.mjs 中未被现有测试覆盖的分支，每条给出能触发它的具体输入",
    "status": "pending",
    "owner_role": "explorer",
    "verified_by": "auditor",
    "acceptance": "清单逐条点名文件中的分支并给出具体输入；auditor 能通过阅读源码确认每一条分支真实存在",
    "files": ["plugins/teamwork/lib/journal.mjs"],
    "blocked_by": []
  },
  {
    "id": "tests",
    "deliverable": "为 survey 列出的边界各写一个测试，落在 tests/journal-boundary.test.mjs",
    "status": "pending",
    "owner_role": "worker",
    "verified_by": "critic",
    "acceptance": "npm test 全绿；且每个新测试都被证明在对应分支被破坏时会失败（改坏该分支 → 看它失败 → 还原）。新文件必须被 npm test 引用（结构校验会强制这一点）",
    "files": ["tests/journal-boundary.test.mjs"],
    "blocked_by": ["survey"]
  }
]
```

> **注意字段名**：是 `owner_role` / `verified_by`，不是 `owner` / `verifier`。
> 文件必须是**纯 JSON 数组**，不是 `{"milestones": [...]}`。

```bash
node $CLI plan --milestones milestones.json
node $CLI schedule          # 看批次与派发数
```

**看点**：`plan` 会拒绝不合规的计划——比如两个里程碑抢同一个文件、或验证者就是实现者。

## 第 4 步：设定小额预算

编辑 `.teamwork/campaign.json`，加上：

```json
"spawnBudget": 6
```

## 第 5 步：批准并交给它干

```bash
node $CLI approve
```

**这是唯一允许执行的闸门。** 批准前它是不会动的。

然后在 ZCode 里：

```
/teamwork 补齐 lib/journal.mjs 的边界测试
```

## 观察点（这是本次任务真正的目的）

跑的时候盯这五处，它们分别对应五个已修复的真机机制：

| # | 看什么 | 期望 | 对应机制 |
| --- | --- | --- | --- |
| 1 | **访谈**是否正常提问 | 分几批问清目标/约束/验收 | 访谈协议 |
| 2 | **Sentinel** 是否给出 `CLEARED` / `BLOCKED` | 有明确判定，不是含糊通过 | 开工前审查 |
| 3 | 让某个 Worker 去写**不属于它**的文件 | 被 **deny** | 文件独占 |
| 4 | 里程碑声称完成、但**没写验证记录**时想收尾 | 被**拦住**，理由点名缺口 | 验证门禁 |
| 5 | 派发数逼近 6 | 出现预警；到顶后**拒绝** | 派发预算 |

**第 4 条是关键**——那是整个项目最难做对、也最值钱的部分。

> ### 2026-09-22 的真跑结果
>
> 完整跑过一轮，结果如下（详见 [实测记录.md](实测记录.md)）：
>
> | # | 结果 | 备注 |
> | --- | --- | --- |
> | 1 | **未测** | 需要真人在 ZCode 里交互，机器无法替代 |
> | 2 | **未测** | 同上 |
> | 3 | ✅ 生效 | A 占住文件后 B 被 deny；B 用 Bash 绕过同样被 deny |
> | 4 | ✅ 生效 | 模型被拦回，自己把状态从 `done` 改回 `pending` |
> | 5 | ✅ 生效 | 上限 3 时前 3 次放行、第 4 次拒绝 |
>
> 5 项里 3 项按预期，达到下方达标线。
>
> 第 4 条还做了对照实验排除「模型本来就爱整理状态」：
> 只有「门禁开 + 状态有矛盾」这一种组合会触发修改。
>
> **同一次真跑还暴露了 3 个缺陷**（安装路径、BOM 静默解除钩子、预算两边账不一致），
> 以及**一次针对测试的作弊**——模型伪造了一个 `git` 可执行文件让 skipped 的测试变绿。
> 这些都已修复并记入 [实测记录.md](实测记录.md)。
