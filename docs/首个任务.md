# 首个任务

> 第一次用 Teamwork 时跑这个。**目标不是产出，是让你看清它到底怎么工作。**
>
> 任务故意选得小、边界清晰、验收可验证。跑完你就知道它值不值得用在真活上。

---

## 为什么是这个任务

| 考虑 | 说明 |
| --- | --- |
| **安全** | 目标仓库就是本仓库。跑坏了也不碰你的真实项目 |
| **小** | 2 个里程碑，串行，不涉及并发写 |
| **可验证** | 验收标准是 `npm test` 通过 + 新测试先失败后通过 |
| **有真实空白** | `lib/journal.mjs` 确实有未覆盖的边界分支 |

---

## 前置检查（三项，缺一不可）

```bash
# 1. 版本必须是 v0.3.2 或至少 v0.3.1（含全部 7 个真机修复）
node -p "require('./package.json').version"

# 2. 本地测试全绿（804 项）
npm test

# 3. ZCode 里已经：
#    - 安装本仓库为 marketplace
#    - 安装 teamwork 插件
#    - 【开新会话】← 钩子配置是会话启动时快照的
#    - 【批准钩子信任】← 未批准前钩子完全不执行
```

---

## 第 1 步：建立 campaign

```bash
CLI=plugins/teamwork/lib/teamwork-cli.mjs

node $CLI init --objective "补齐 lib/journal.mjs 的边界测试：先把未覆盖的分支找出来并逐条说明触发输入，再为其中每一条写一个测试"
```

**看点**：`init` 会创建 `.teamwork/campaign.json`，此时是 `scoping` 阶段，**还不能执行**。

## 第 2 步：看拆解草稿，然后自己定计划

```bash
node $CLI decompose
```

它会按规则给一版草稿。**草稿只是脚手架**，真实计划用下面这份。

## 第 3 步：写里程碑文件

存成 `milestones.json`：

```json
[
  {
    "id": "survey",
    "deliverable": "列出 lib/journal.mjs 中未被现有测试覆盖的分支，每条给出能触发它的具体输入",
    "status": "pending",
    "owner_role": "explorer",
    "verified_by": "auditor",
    "acceptance": "清单逐条点名文件中的分支并给出具体输入；auditor 能通过阅读源码确认每一条分支真实存在",
    "files": ["plugins/teamwork/lib/journal.mjs"],
    "blocked_by": []
  },
  {
    "id": "tests",
    "deliverable": "为 survey 列出的边界各写一个测试，落在 tests/journal-boundary.test.mjs",
    "status": "pending",
    "owner_role": "worker",
    "verified_by": "critic",
    "acceptance": "npm test 全绿；且每个新测试都被证明在对应分支被破坏时会失败（改坏该分支 → 看它失败 → 还原）。新文件必须被 npm test 引用（结构校验会强制这一点）",
    "files": ["tests/journal-boundary.test.mjs"],
    "blocked_by": ["survey"]
  }
]
```

> **注意字段名**：是 `owner_role` / `verified_by`，不是 `owner` / `verifier`。
> 文件必须是**纯 JSON 数组**，不是 `{"milestones": [...]}`。

```bash
node $CLI plan --milestones milestones.json
node $CLI schedule          # 看批次与派发数
```

**看点**：`plan` 会拒绝不合规的计划——比如两个里程碑抢同一个文件、或验证者就是实现者。

## 第 4 步：设定小额预算

编辑 `.teamwork/campaign.json`，加上：

```json
"spawnBudget": 6
```

## 第 5 步：批准并交给它干

```bash
node $CLI approve
```

**这是唯一允许执行的闸门。** 批准前它是不会动的。

然后在 ZCode 里：

```
/teamwork 补齐 lib/journal.mjs 的边界测试
```

---

## 观察点（这是本次任务真正的目的）

跑的时候盯这五处，它们分别对应五个已修复的真机机制：

| # | 看什么 | 期望 | 对应机制 |
| --- | --- | --- | --- |
| 1 | **访谈**是否正常提问 | 分几批问清目标/约束/验收 | 访谈协议 |
| 2 | **Sentinel** 是否给出 `CLEARED` / `BLOCKED` | 有明确判定，不是含糊通过 | 开工前审查 |
| 3 | 让某个 Worker 去写**不属于它**的文件 | 被 **deny** | 文件独占 |
| 4 | 里程碑声称完成、但**没写验证记录**时想收尾 | 被**拦住**，理由点名缺口 | 验证门禁 |
| 5 | 派发数逼近 6 | 出现预警；到顶后**拒绝** | 派发预算 |

**第 4 条是关键**——那是整个项目最难做对、也最值钱的部分。

## 成本预期

| 项 | 期望 |
| --- | --- |
| 派发数 | 2~4 次 |
| 时长 | 几分钟到十几分钟 |
| token | 比普通对话多 1~2 个数量级 |

**如果远超这个范围，就停下来报告**——那说明有问题。

---

## 什么算"这次试验成功"

- ✅ 5 个观察点里**至少 3 个**按预期工作
- ✅ 没有卡死、没有失控的 token 消耗
- ✅ 你**能看懂它在干什么**（不是黑箱）

**别期待它一次完美。** 第一轮的任务是**摸清它的脾气**，不是产出完美代码。
